# Plan 4: End-to-end tests for compiler, starter and the published packages

Status: proposed
Order: runs alongside Plan 2 (its CI area) and before Plan 3; Plan 1 Phase 6.6 (`e2e/compiler-e2e`) is superseded by section 5 of this plan
Owner: TBD

## 1. Goal

Prove, on every pull request and every night, that the published Rockpack packages work end to end for a real user: a project generated by `@rockpack/starter` installs, lints, tests, builds and serves; every documented `@rockpack/compiler` configuration produces a working bundle; and all of this holds with **current dependency versions**, not only with the versions frozen in the monorepo lockfile.

The compiler and the starter are the key modules and get the deepest coverage.

## 2. How e2e works today

| Suite | What it does | Gaps |
|---|---|---|
| `e2e/babel-e2e` | 4 tests calling `createBabelPresets` from the built `@rockpack/babel` | Unit-level checks; duplicates Plan 1 Phase 2. Only the ESM entry is exercised. |
| `e2e/starter-e2e` `simple-flow.spec.ts` | `-v`, `-h`, "no name" through the built CLI | The "no name" test passes when nothing throws. No invalid-type, existing-directory, `--folder` or `.` cases. |
| `e2e/starter-e2e` `generators.spec.ts` | Generates 8 projects (`csr`, `ssr`, `component`, `library` × with/without tests) with `--no-install --mode=test --folder=generators`; checks a handful of files; runs `npm run lint`, `npm test`, `npm run build` inside each; serves csr/ssr in dev and after build and compares strict pixel screenshots with Homebrew Chromium | **Dependencies are never installed.** The generated `package.json` lists the latest versions inside each major (resolved through `latest-version`, so the network is needed), but the projects resolve modules from the hoisted root `node_modules`, whose versions are whatever `e2e/starter-e2e/package.json` pins by hand. The suite therefore tests neither the versions it writes nor the install experience. | `examples/compiler/*` (20) | Real projects for frontend (styles, vendor, banner, custom html, dotenv, eslint/debug, imagemin, svg, css-modules, ts-css-modules, postcss, mdx, antd, analyzer, typescript, elm with custom modules/plugins), backend (`nodejs` with alias), isomorphic (express), library (string form; object form with esm/cjs/externals; `source-ts`) | No script builds them in CI and nothing asserts their output. They are the only compiler e2e corpus. | `examples/tester/*` (10) | Run by root `npm test` | Fine as smoke tests; structure issues handled in Plan 2 I1/I2. |

Additional facts that shape the design:

- `--mode=test` pins `@rockpack/*` to the starter's own version (`8.0.0`), which resolves to the workspace symlinks when the generated project is inside the monorepo. Outside the monorepo it would resolve to the **published** `8.0.0` from npm, not the local build.
- In dev mode the compiler calls `find-free-port` starting at 3000, so a test cannot assume the port; it has to read it from the child's output.
- `puppeteer@25` downloads Chromium in a postinstall script; npm 11 does not run it until the script is approved (`npm approve-scripts`), so CI must run `npx puppeteer browsers install chrome` explicitly.
- `book` is prerendered with a local `/Applications/Chromium.app` and is out of scope here (Plan 3 R1).

## 3. Design

### 3.1 Two dependency modes

Every suite that builds or runs a project supports two modes, selected with `E2E_DEPS=pinned|latest`:

- **pinned** (pull-request gate): deterministic and offline after `npm ci`. Generated projects and fixtures resolve modules from the monorepo lockfile. The test helper rewrites the generated `package.json` versions to the lockfile versions (`e2e/tools/pin-to-lockfile.ts` reads `package-lock.json`) so that the file and the runtime agree.
- **latest** (nightly, manual, and release gate): the generated project is really installed with `npm install` in an empty temp directory outside the monorepo. `@rockpack/*` come from tarballs produced by `npm pack` of the local packages (section 6), everything else resolves to the newest version allowed by `versions.json` majors, exactly as a user would get today. After install the suite asserts `npm outdated --json` reports nothing behind `wanted` (so the project really runs on current versions) and records the packages where `latest` is a major ahead of `wanted` in the job summary, which is the signal to bump `versions.json`.

### 3.2 Dependency canary

A nightly `deps-canary` job checks that the monorepo itself still works with current versions: on a throwaway branch it runs `npm run updater -- --no-major` (peer-aware, see the 2026-09-23 change) and, separately, `npm run updater` including majors, then `npm ci`-equivalent install, `npm run build`, `npm run test:unit`, the compiler and starter suites in pinned mode, and the compiler examples build. A failure opens or updates a GitHub issue ("Dependency canary failed") with the list of bumped versions and the failing step. This is how "e2e passes with current dependencies" is enforced continuously instead of being discovered on the next manual update.

### 3.3 Layout

```
e2e/
  tools/                 shared helpers (workspace, not published)
    run.ts               spawn with process-group kill, timeout, output capture, ANSI strip
    ports.ts             free port lookup, "wait for URL", parse "listening on" lines
    fs.ts                exists, temp dirs, file tree snapshot
    pack.ts              npm pack every package into e2e/.tarballs, rewrite package.json to file: specs
    pin-to-lockfile.ts   rewrite versions to package-lock.json versions (pinned mode)
    browser.ts           puppeteer launch with bundled Chromium, DOM helpers
  babel-e2e/             kept as a packaging smoke test (section 6)
  compiler-e2e/          section 5
  starter-e2e/           section 4 (rewritten)
  packaging-e2e/         section 6
```

All suites use `@rockpack/tester` with `testEnvironment: 'node'`, `runInBand`, explicit per-test timeouts, and the negative/positive `describe` structure from CLAUDE.md. Generated files go to `os.tmpdir()` unless `E2E_KEEP=1` is set, in which case they stay under `e2e/<suite>/.out/` (gitignored) for inspection.

## 4. Starter e2e (key module)

Rewrite `e2e/starter-e2e` in four layers. Every layer is a separate spec file and can run alone.

### 4.1 CLI contract (`cli.spec.ts`, fast, no generation)

Negative cases: no project name exits 1 with "Please specify the project directory" (assert with `expect(() => run()).toThrow`); unknown `--type` exits 1 with the list of valid types; target directory exists and is not empty exits 1; Node below the minimum version prints the requirement (run with a fake `process.versions.node` through `NODE_OPTIONS=--require`).
Positive cases: `-v`/`--version` prints `Rockpack v<version>`; `-h`/`--help` prints usage; `--folder` places the project under the folder; `.` inside an empty directory names the project after the directory; `.` inside a git repository names it after the basename with spaces replaced.

### 4.2 Generation (`generation.spec.ts`, `--no-install`, pinned mode)

For each of `csr`, `ssr`, `component`, `library` × `--tests=true|false` (8 projects, generated once in `beforeAll` of the matrix):

- the file tree matches a golden list stored in `e2e/starter-e2e/golden/<type>-<tests>.txt` (sorted relative paths; the test prints a diff on mismatch and `E2E_UPDATE_GOLDEN=1` rewrites it);
- `package.json` matches a golden snapshot with versions normalised to `<major>` (scripts, `exports`, `main`, `types`, `peerDependencies`, `lint-staged` and hook scripts are asserted exactly);
- `.env` exists when the template ships `.env.example`; `.gitignore`, `.gitattributes` and, for library/component, `.npmignore` and `example/package.json` exist;
- `git init` happened (`.git` exists) and, after Plan 2 E2, the hooks are installed (`.husky/*` or `simple-git-hooks` entries);
- `CLAUDE.md` from the `claude` addon is present.

### 4.3 Project quality (`quality.spec.ts`, both modes)

For each generated project: `npm run lint` passes; `npm test` passes and prints the tester success marker for `*-with-tests`; `npm run build` passes and the artifact list matches a golden list per type (csr: `index.html`, `index.js`, `vendor.js`, `styles.css`, `favicon.ico`, licence files; ssr: `dist/index.js` plus `public/*`; library: `lib/esm/index.mjs`, `lib/cjs/index.cjs`, `dist/types/index.d.ts`; component: the same plus `dist/css/styles.css`); for library and component, `npm run build:example` builds the `example/` app; `npm pack --dry-run` lists only the files the template intends to publish.
In **latest** mode the projects live outside the monorepo, are installed for real (section 3.1), and `npm outdated` must be clean.

### 4.4 Runtime (`runtime.spec.ts`, browser, both modes)

- **csr dev:** start `npm start`, read the dev-server URL from stdout (the compiler picks a free port), open it with puppeteer (bundled Chromium), assert `document.title`, the rendered root text and that the stylesheet applied (`getComputedStyle` of a known element); edit `src/index.tsx`, wait for the HMR update message in stdout and assert the new text on the page; stop the process group.
- **csr build:** serve `dist/` with a tiny static server on a free port (replaces `csr.server.ts`); same DOM assertions plus a check that `vendor.js` and `index.js` are both requested.
- **ssr dev:** start `npm start` (isomorphic: SsrDevelopment, nodemon, livereload), wait for the backend URL, `fetch` it and assert the HTML already contains the rendered markup (no client render); edit the server file and assert nodemon restarts (log line) and the page still answers; stop.
- **ssr build:** `node dist/index.js`, `fetch` the HTML, assert SSR markup, assert the `public/` assets are served; open in the browser and assert hydration happened (a click handler works).
- One loose screenshot per type (`looks-same` with tolerance and `ignoreAntialiasing`) kept as a visual smoke check, generated on Linux in CI, never strict.

Timeouts per step are explicit (generation 60 s, install 5 min, build 3 min, server start 60 s). Ports come from `e2e/tools/ports.ts`; livereload port 35729 is passed to the generated project through `LIVE_RELOAD_PORT` once the compiler supports it (until then the suite asserts the port is free before starting and kills the process group after).

### 4.5 Starter-side changes needed

- `--no-install` must still write the exact versions it resolved (it does); add `--registry-timeout` so a slow registry fails fast instead of hanging the suite.
- Plan 2 E2 (hooks) and E1 (version check offline) are prerequisites for the hook and offline assertions.
- Keep `--mode=test` resolving the latest versions inside majors: it is what latest mode relies on. Plan 3 ST2 is amended to add an `--offline` flag instead of changing `--mode=test`.

## 5. Compiler e2e (key module)

New workspace `e2e/compiler-e2e`. Fixtures are small real projects under `e2e/compiler-e2e/fixtures/`, each with `src/`, `tsconfig.json`, `package.json` (no dependencies of its own; modules resolve from the monorepo in pinned mode and from an installed copy in latest mode). Every test copies the fixture into a temp directory, runs the compiler through a `scripts.build.ts` in a child process (`tsx`, `NODE_ENV` set explicitly), and asserts on the output. Running in a child process keeps `process.exit` inside the compiler from killing Jest and makes the dev-server tests possible before Plan 3 C9 adds `stop()`.

### 5.1 Production builds (`build.spec.ts`)

| Fixture | Config under test | Assertions |
|---|---|---|
| `frontend-basic` | `frontendCompiler()` defaults | `dist/index.html` references `index.js`; bundle executes in jsdom and renders the root text; sourcemap present in dev, absent or hidden in prod per `debug` |
| `frontend-full` | `styles`, `vendor`, `banner: true`, `html: { template, favicon, code }`, `copy: [{from,to}]`, `global`, `version`, `port` | `styles.css` extracted; `vendor.js` contains react and `index.js` does not; banner text at the top of `index.js` (read `banner` from `package.json`); `favicon.ico` and copied files present; `html.code` injected; `DefinePlugin` values visible in the bundle; version in the html filename or meta as implemented |
| `frontend-dotenv` | `.env`, `.env.example`, `.env.defaults` | values present, `process.env` object not leaked, missing required var from `.env.example` fails the build |
| `frontend-styles` | css modules, ts css modules (d.ts generation), scss, postcss config in project, tailwind v4 | class names hashed, `*.module.css.d.ts` emitted, tailwind utilities present |
| `frontend-assets` | svg (component and url), images through imagemin, fonts, markdown/mdx, json, wasm rule | expected files in `dist`, sizes below thresholds, mdx compiled |
| `frontend-ts` | TypeScript with decorators, `ForkTsChecker` errors | a type error fails the build with the file and line in the output; a valid project passes |
| `frontend-lint` | eslint and stylelint present, `debug` on and off | lint errors fail the build only when `debug` is off, as implemented |
| `frontend-analyzer` | `analyzer: true` in prod | static report file emitted |
| `backend-basic` | `backendCompiler()` with `nodejs` externals, `global.ROOT_DIRNAME` | `dist/index.js` runs with `node`, prints the expected output, `node_modules` not bundled |
| `isomorphic-basic` | `isomorphicCompiler(frontend, backend)` | both bundles produced; `node dist/index.js` serves HTML with SSR markup; `LIVE_RELOAD_PORT` absent in prod |
| `library-umd` | `libraryCompiler('MyLib')` | `dist/index.js` is UMD; `require()` and `<script>` in jsdom both expose `MyLib` |

| `source-only` | `sourceCompiler({ esm, cjs, types })` | per-file output with `.mjs`/`.cjs` extensions rewritten in imports, assets copied, specs excluded (Plan 1 Phase 0.3), d.ts emitted |
| `config-only` | `makeWebpackConfig()` and `configOnly` | returns a serialisable config, no files written, callback receives `(config, modules, plugins, mode)` and can `modules.add/modify/remove` and `plugins.set` (the elm example pattern) |

Negative cases in the same file: missing entry file fails with the compiler's message; invalid `libraryCompiler` options fail; `isomorphicCompiler` without a backend fails; production build with a runtime error in the bundle still exits non-zero after Plan 2 F.

### 5.2 Development mode (`dev.spec.ts`)

- `frontend-basic` in dev: start, parse the URL, `fetch` the page and the hot-update endpoint, edit a source file and expect a rebuild message, stop. Assert `open: false` is honoured with `_rockpack_testing`.
- `isomorphic-basic` in dev: SsrDevelopment starts nodemon, livereload answers on its port, editing the server restarts it, editing the client triggers a browser reload script in the HTML.
- `backend-basic` in dev: NodemonPlugin restarts on change and the inspect port message is printed once.
- `port` option respected when free; falls forward to a free port when busy (start a dummy listener first).

### 5.3 Examples as a regression corpus (`examples.spec.ts`)

Build every `examples/compiler/*` in production (`lerna run build --scope='@rockpack/example-compiler-*'` in CI, and in this spec for local runs) and assert the expected artifact list per example from a table in `e2e/compiler-e2e/examples.golden.json`. Examples that need external binaries (`advanced-config-elm-support` needs the `elm` compiler) are marked optional and skipped when the binary is missing.

### 5.4 Compiler-side changes needed

- A `stop()` on the dev-server result and a `port` reported through the result or a log line with a stable format (`[rockpack] dev server: http://localhost:<port>`), so tests do not scrape webpack's output. Until Plan 3 C9 lands, the suite scrapes the current output behind one helper.
- Honour `LIVE_RELOAD_PORT` from the environment when set, so parallel suites do not collide on 35729.
- Plan 2 F (typed errors, non-zero exit codes) is what makes the negative cases assertable.

## 6. Packaging e2e (all packages)

New workspace `e2e/packaging-e2e`. Once per run, `e2e/tools/pack.ts` runs `npm pack` for `babel`, `codestyle`, `compiler`, `starter`, `tester`, `tsconfig`, `utils` into `e2e/.tarballs/`. Then, in a temp project outside the monorepo with `npm install ./e2e/.tarballs/*.tgz`:

- each package's `exports` map resolves: `import()` the ESM entry and `require()` the CJS entry, assert the main export exists (`createBabelPresets`, `makeConfig`, `frontendCompiler`, `tester`, `getMode`), and `tsc --noEmit` on a consumer file that imports the types (catches broken `types` paths and missing d.ts);
- `npx rockpack -v` works from the installed `@rockpack/starter` binary;
- the tarball file lists match `files` and contain no specs, fixtures, coverage or maps that should not ship;
- `@rockpack/tsconfig` extends correctly from a consumer `tsconfig.json`.

`e2e/babel-e2e` shrinks to the ESM/CJS smoke test of `@rockpack/babel` or is folded into this workspace. _Decision 2026-09-24 (Plan 2 I3): it stays as a smoke test of the built ESM and CJS entries (loaded in real Node processes) plus the `import.meta`/`__filename` integration spec under `@rockpack/tester`; the packaging workspace covers installed tarballs._

## 10. Risks

- **Registry flakiness in latest mode.** Retry installs once, cache `~/.npm` in CI, and never let latest mode gate a PR.
- **Free-port races.** Ports are reserved by the helper and released only to the child process; suites run in band.
- **Runtime cost.** Runtime and latest jobs are separate from the PR gate; fixtures are minimal; builds reuse the webpack filesystem cache within a job.
- **Golden drift.** Golden lists are updated only through `E2E_UPDATE_GOLDEN=1` and reviewed in the PR diff.
- **Chromium in CI.** Use puppeteer's pinned browser; do not rely on system browsers.
